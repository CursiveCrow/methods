## What CESAR takes in and produces

The abstract and Figure 1 give two inputs:

1. an algorithmic **description program** for communicating sequential
   processes, in a high-level language inspired by CSP; and
2. **specification formulas** in the paper's branching-time logic.

The translator converts the program to a **model: IPN**. A step drawn between
the IPN and the analyzer produces the predicate transformer `pre`; the
analyzer also receives the specification formulas. Figure 1's only named
output is **diagnostics**. The paper does not define the format or content of
those diagnostics and does not show a diagnostic or counterexample trace.

CESAR's progressive validation has two stated aspects (original p. 337):

- coherence of data manipulation, including static characteristics of data
  and exchanged variables, visibility, and access rights; and
- validation of dynamic behavior against specifications.

The paper develops the second aspect. It does not present a synthesis
algorithm, a refinement proof from source language to implementation, or a
formal account of all static checks.

## Description language and synchronization model

### Program constructs

Section 2.1 (original p. 339) treats a system as communicating sequential
processes. A communication name is an **exchanged variable**. Output
`!V := exp` in one process rendezvous with input `?V` in another; the receiving
process has a local copy also called `V`. Processes may also have internal
variables, which cannot communicate. Variables are typed; the source says
that usual types and type constructors are available and also permits
non-specified types whose manipulation rules need not be made explicit.

The basic statement is vector assignment. Input or output may occur
simultaneously with such an assignment. `nop` is the assignment whose
right-hand side is the identity function.

The two displayed nondeterministic compounds are, literally,

```text
if b1 -> s1 // b2 -> s2 // ... fi
do b1 -> s1 // b2 -> s2 // ... od
```

`IF` waits until a guard is true and then executes a corresponding statement
sequence. `DO` repeats that behavior until an `EXIT` is encountered in a
selected sequence. When several guards are true, selection is
nondeterministic. If a sequence begins with input or output, rendezvous
availability implicitly strengthens its guard. The source compares these to
the `WHEN` and `CYCLE` statements of [Brinch Hansen 78]. It gives this feature
description, not a complete grammar or a rule-by-rule operational semantics.

### Interpreted Petri nets

An **Interpreted Petri Net (IPN)** is defined on original p. 340 as a Petri
net together with:

- a vector of variables `X`; and
- a mapping from each net transition to a guarded command
  \(c_i\mathbin{\to}a_i\), where \(c_i\) is a condition on `X` and
  \(a_i=(X:=\alpha_i(X))\) is a vector assignment.

This is the paper's program model: a transition fires only when Petri-net
firing conditions and its associated condition permit it, and firing
executes the associated assignment. The always-true condition and identity
assignment are omitted from a graphical inscription. A transition without
an inscription therefore fires as in an ordinary Petri net.

The translator also type-checks and deletes internal variables of
non-specified types. It translates each sequential process with graph-grammar
rules cited to [Queille 81], then composes process IPNs by merging transitions
that perform a rendezvous. The paper asserts that each sequential-process net
is a safe state graph and that the merge preserves the safety of each
process. The analyzer later uses those facts to simplify Boolean predicates.
No translation grammar, preservation theorem, or proof is included here.

## Complete alternating-bit example

### Stated behavioral assumptions

The example is a one-direction presentation of the symmetric alternating-bit
protocol (original pp. 340--341). Transmission errors are treated as losses.
The sender alternates the bit only after receiving the matching
acknowledgement. After an arbitrary but finite local delay it retransmits a
message without changing its bit. The receiver analogously retransmits its
previous acknowledgement after an arbitrary local delay and skips duplicate
messages. The source states the additional assumption that the line “cannot
loose all the messages and acknowledgements (i.e. the line is not cut).”

Two non-specified types are introduced: `data`, the data part of a message,
and `pattern`, a bit pattern recognized as an acknowledgement. With standard
type `boolean`, the displayed structures are:

```text
type msg = ( MESSAGE : data ;
             B : boolean ) ;
type ack = ( ACKNOWLEDGEMENT : pattern ;
             B : boolean ) ;
```

The program uses `T` for true and prefix `^` for Boolean complementation.

### Four displayed processes

Original pp. 342--343 contain four processes. The following inventory keeps
the printed labels and assignments; it is not a replacement language.

- `SENDER` has output `M:msg`, input `A:ack`, data `X`, and initially false
  bit `Y`. `send` outputs `M := (X,Y)`. It then nondeterministically receives
  an acknowledgement (`receiveack`) or repeats the same message (`repeat`).
  `acceptack` tests `A.B = Y`, complements `Y`, and exits the inner loop;
  `skipack` tests `A.B ≠ Y` and performs `nop`.
- `RECEIVER` has input `MM:msg`, output `AA:ack`, and initially false bit
  `Z`. `receive` inputs `MM`. `accept` tests `MM.B = Z` and exits the inner
  loop; `skip` tests `MM.B ≠ Z`. `repeatack` outputs
  `AA := ("ack", ^Z)`. After acceptance, `sendack` outputs
  `AA := ("ack", Z)` and complements `Z`.
- `SENDTORECEIVE` inputs `M` and outputs `MM`. After `get`, its two true-
  guarded choices are `transmit`, assigning `MM := M`, and `loose`, doing
  `nop`.
- `RECEIVETOSEND` inputs `AA` and outputs `A`. After `getack`, its choices are
  `transmitack`, assigning `A := AA`, and `looseack`, doing `nop`.

The English non-loss assumption is not encoded in these four displayed
processes: both line processes may choose their true-guarded `loose` branch
on every iteration. Section 3 gives no fairness clause that rules out an
infinite sequence of losses. Consequently, the non-loss assumption must be
kept as a stated external assumption; the printed program alone does not
realize it.

### Figure 2

Figure 2 (original p. 343) is the IPN produced from that description. It has
four safe-state-graph components and initially marked places:

- sender places `s1`, `s2`, `s3`, initially `s1`;
- receiver places `r1`, `r2`, `r3`, initially `r1`;
- sender-to-receiver line places `m1`, `m2`, initially `m1`; and
- receiver-to-sender line places `a1`, `a2`, initially `a1`.

The drawing exposes the rendezvous merges and inscriptions:

- `send/get` and `repeat/get`, both with `M := (X,Y)`;
- `transmit/receive` with `MM := M`, and separate `loose`;
- receiver `accept` guarded by `MM.B = Z` and `skip` by `MM.B ≠ Z`;
- `sendack/getack` with `AA := ("ack",Z), Z := ^Z` and
  `repeatack/getack` with `AA := ("ack",^Z)`;
- separate `looseack`;
- `transmitack/receiveack` with `A := AA`;
- sender `skipack` guarded by `A.B ≠ Y`; and
- sender `acceptack` guarded by `A.B = Y`, assigning `Y := ^Y`.

Thus Figure 2 is both the only net figure and the concrete bridge from the
four-process program to the Boolean predicates used in §4.3. The paper gives
no separate state-count, transition-count, reachability graph, or complete
enumeration of its markings.

## Literal logic, transition structures, and semantics

### Formula vocabulary

Section 3.1 calls the specification language a branching-time logic `L`.
Eliminating its prose but not adding operators, its formula vocabulary is

\[
 f ::= p\mid \mathrm{true}\mid \mathrm{false}\mid \neg f
       \mid f\land f\mid f\lor f\mid f\Rightarrow f
       \mid \mathrm{POT}(f)\mid \mathrm{INEV}(f),
 \qquad p\in F.
\]

The two printed abbreviations are exactly

\[
 \mathrm{ALL}(f)=\neg\mathrm{POT}(\neg f),\qquad
 \mathrm{SOME}(f)=\neg\mathrm{INEV}(\neg f).
\]

`POT` and `INEV` are unary state-formula operators; the syntax has no separate
path-formula category. Branch quantification is embedded in their semantic
clauses.

### Transition-system and path convention

The paper writes a transition system as \(S=(Q,\to)\), with
\(\to\subseteq Q\times Q\); \(q\to q'\) means that an executable action at
`q` leads to `q'`. An execution sequence may be infinite or finite, but a
finite one must end at a sink \(q_t\), meaning
\(\neg\exists q''(q_t\to q'')\). `EX_q` denotes all execution sequences from
`q`.

For a finite sequence, the authors adjoin a fictitious inaccessible state
\(\omega\) to `Q` and put \(s(k)=\omega\) whenever the `k`th element is not
defined. They stipulate that
\(s(0)\mathrel{\xrightarrow{k}}s(k)\) holds exactly when
\(s(k)\ne\omega\). This makes the universal `k` clauses below range only over
positions actually present on a finite maximal execution.

There is a literal formal omission here. The printed sentence defining an
“execution sequence from a given state \(q_0\)” states only the finite-sink
condition. It does **not** explicitly include \(s(0)=q_0\) or
\(s(i)\to s(i+1)\) for successive positions. Those clauses are required by
the ordinary meaning and later use of “execution sequence,” but they are not
on the page and must not be represented as fully printed definitions.

### Interpretation clauses

An interpretation `| |` assigns each atomic \(p\in F\) a predicate
\(|p|:Q\to\{tt,ff\}\). The source explicitly prints clauses for `true`,
negation, conjunction, and the temporal operators. Using its indexed-arrow
notation, the temporal clauses are:

\[
\begin{aligned}
 |\mathrm{POT}(f)|(q)
 &\iff \exists s\in EX_q\;\exists k\in\mathbb N\,
       [q\mathrel{\xrightarrow{k}}s(k)\land |f|(s(k))],\\
 |\mathrm{INEV}(f)|(q)
 &\iff \forall s\in EX_q\;\exists k\in\mathbb N\,
       [q\mathrel{\xrightarrow{k}}s(k)\land |f|(s(k))].
\end{aligned}
\]

Accordingly, `POT(f)` says that some execution reaches an `f` state, while
`INEV(f)` says that every maximal execution reaches an `f` state. Both may be
witnessed at `k=0`, so they include the current state.

Expanding the two dual abbreviations, the paper prints:

\[
\begin{aligned}
 |\mathrm{ALL}(f)|(q)
 &\iff \forall s\in EX_q\;\forall k\in\mathbb N\,
 [q\mathrel{\xrightarrow{k}}s(k)\Rightarrow |f|(s(k))],\\
 |\mathrm{SOME}(f)|(q)
 &\iff \exists s\in EX_q\;\forall k\in\mathbb N\,
 [q\mathrel{\xrightarrow{k}}s(k)\Rightarrow |f|(s(k))].
\end{aligned}
\]

Thus `ALL(f)` requires `f` at every defined state of every maximal execution,
and `SOME(f)` requires one maximal execution all of whose defined states
satisfy `f`. The \(\omega\) convention makes the implication vacuous beyond
the end of a finite execution.

The list does not print separate interpretation clauses for `false`,
disjunction, or implication, although those were named as primitive logical
connectives. Their ordinary Boolean readings are evidently intended, but a
source-faithful account must record that the displayed semantic definition is
formally incomplete at those three clauses.

In later standard CTL notation, and only as a comparison rather than source
terminology, the four operators have the state-formula behavior
`POT = EF`, `INEV = AF`, `ALL = AG`, and `SOME = EG`, with maximal finite
paths handled by the paper's \(\omega\) device. The language allows Boolean
combination and nesting of these unary forms, but supplies neither a next
operator nor an until operator. It is therefore not the full later CTL
grammar and not CTL*: there is no independent path-formula grammar or
arbitrary temporal combination along paths. The chapter itself does not use
the phrase “model checking”; it calls the activity analysis, verification,
and “proving specifications in CESAR.”

## Source-defined program predicates and all property examples

The propositional variables used for a program formula are (original p. 345):

- predicates on variables of specified types;
- `Init`, characterizing all possible initial control and data states; and
- for each labeled action `a`, `enable a`, the states from which `a` can be
  executed, and `after a`, the states reached immediately after `a`
  terminates.

For a finite action set and a process `P`, the printed abbreviations are

\[
\begin{aligned}
 \mathrm{enable}(a_1,\ldots,a_k)&=\bigvee_{i=1}^k\mathrm{enable}\ a_i,\\
 \mathrm{enable}\ P&=\mathrm{enable}\ A(P),\\
 \mathrm{after}(a_1,\ldots,a_k)&=\bigvee_{i=1}^k\mathrm{after}\ a_i,
\end{aligned}
\]

where `A(P)` is the set of actions of process `P`.

### Invariants

The invariant schema is

\[
 \mathrm{Init}\Rightarrow\mathrm{ALL}(P),
\]

where `P` uses only logical operators. The three AB examples are:

\[
\begin{aligned}
\mathrm{Init}&\Rightarrow
 \mathrm{ALL}(\mathrm{after}(send,repeat)\Rightarrow M.B=Y),\\
\mathrm{Init}&\Rightarrow
 \mathrm{ALL}(\mathrm{after}\ receive\Rightarrow MM=M),\\
\mathrm{Init}&\Rightarrow
 \mathrm{ALL}(\mathrm{after}\ receive\Rightarrow MM.B=Y).
\end{aligned}
\]

The accompanying prose says respectively that a sent message carries the
sender's bit, the line does not modify a message, and a received control bit
equals the sender's bit at the same time.

### Liveness and absence of deadlock

The source calls action `a` live when, from every state succeeding an initial
state, some execution can reach a state enabling `a`. Its formula is

\[
 \mathrm{Init}\Rightarrow\mathrm{ALL}\,\mathrm{POT}\,\mathrm{enable}\ a.
\]

For \(\{a_1,\ldots,a_k\}\), liveness of every member is the conjunction of
those formulas, also printed after distributing `ALL` over conjunction as

\[
 \mathrm{Init}\Rightarrow
 \mathrm{ALL}\left(\bigwedge_{i=1}^k
     \mathrm{POT}\,\mathrm{enable}\ a_i\right).
\]

Absence of deadlock for the set instead uses its disjunctive `enable`
abbreviation:

\[
 \mathrm{Init}\Rightarrow
 \mathrm{ALL}\,\mathrm{POT}\,\mathrm{enable}(a_1,\ldots,a_k).
\]

The four examples, said to be listed from weaker to stronger, replace the
final target by `enable(SENDER)`, `enable(RECEIVER)`, `enable send`, and
`enable accept`. The first two are described as absence of deadlock for the
named process; the latter two say that emission and reception of a new
message are live.

These are possibility-of-enablement properties. `ALL POT enable a` does not
say that `a` is selected or occurs on every execution, and no fairness rule
turns enabledness into execution.

### Responses

The two general response schemas are printed as:

\[
\begin{aligned}
\text{possible response:}\quad
 &\mathrm{Init}\Rightarrow
   \mathrm{ALL}(\mathrm{after}\ a\Rightarrow
                \mathrm{POT}\,\mathrm{enable}\ b),\\
\text{inevitably possible response:}\quad
 &\mathrm{Init}\Rightarrow
   \mathrm{ALL}(\mathrm{after}\ a\Rightarrow
                \mathrm{INEV}\,\mathrm{enable}\ b).
\end{aligned}
\]

The conclusion in both cases is about `b` becoming executable, not about
`b` actually executing. The four AB formulas on original p. 347 are:

\[
\begin{aligned}
\mathrm{Init}&\Rightarrow
 \mathrm{ALL}(\mathrm{after}(send,repeat)\Rightarrow
              \mathrm{POT}\,\mathrm{enable}\ receive),\\
\mathrm{Init}&\Rightarrow
 \mathrm{ALL}(\mathrm{after}(sendack,repeatack)\Rightarrow
              \mathrm{POT}\,\mathrm{enable}\ receivack),\\
\mathrm{Init}&\Rightarrow
 \mathrm{ALL}(\mathrm{after}(send,repeat)\Rightarrow
              \mathrm{INEV}\,\mathrm{enable}\ receivack),\\
\mathrm{Init}&\Rightarrow
 \mathrm{ALL}[(\mathrm{after}\ accept\Rightarrow
               \mathrm{INEV}(\mathrm{enable}\ sendack))\land
              (\mathrm{after}\ sendack\Rightarrow AA.B=MM.B)].
\end{aligned}
\]

The second and third formulas literally print `receivack`. No action of that
name occurs in the program: original p. 342 and Figure 2 name the action
`receiveack`. This is a printed identifier defect, not a distinct action.

## Predicate-transformer algebra and exact numbered results

Section 4.1 identifies a unary predicate on `Q` with its characteristic
subset of `Q`, and predicate transformers with maps \(2^Q\to2^Q\). Union and
intersection of transformers are pointwise. For a transformer `h`, the
paper defines its Boolean dual by

\[
 \widetilde h(P)=\overline{h(\overline P)},
\]

and `Id(P)=P`. Its iteration notation is literally

\[
 h^*=\mathrm{Id}\cup h\cup h^2\cup\cdots
     =\bigcup_{i\in\mathbb N}h^i,
 \qquad
 h^x=\mathrm{Id}\cap h\cap h^2\cap\cdots
     =\bigcap_{i\in\mathbb N}h^i.
\]

The superscript on the descending iteration is a printed lower-case `x`, not
a later standard greatest-fixed-point symbol. Its definition, not its glyph,
controls its meaning.

There are exactly one numbered definition and two numbered propositions in
the chapter. There are no numbered lemmas or theorems.

### Definition 1 (original p. 347)

For \(P\subseteq Q\),

\[
 \mathrm{pre}(P)(q)\iff
 \exists q'\,(q\to q'\land P(q')).
\]

Thus `pre(P)` is the set of states with at least one immediate successor in
`P`; its dual
\(\widetilde{\mathrm{pre}}(P)=
 Q\setminus\mathrm{pre}(Q\setminus P)\)
is the set whose immediate successors, if any, all lie in `P`.

### Proposition 1 (original p. 347)

For a formula `f`, an image-finite transition relation, and an interpretation
of `L`:

\[
\begin{aligned}
 |\mathrm{ALL}(f)|
   &=\widetilde{\mathrm{pre}}^{\,x}|f|,\\
 |\mathrm{SOME}(f)|
   &=(\mathrm{Id}\cap
      (\mathrm{pre}\cup\widetilde{\mathrm{pre}}))^x|f|.
\end{aligned}
\]

The `pre` disjunct in the second line advances along a chosen successor; the
dual-`pre` disjunct also retains a sink, where there is no successor outside
the current approximation.

### Proposition 2 (original pp. 347--348)

Under the same image-finiteness and interpretation hypotheses:

\[
\begin{aligned}
 |\mathrm{POT}(f)|
   &=\mathrm{pre}^{*}|f|,\\
 |\mathrm{INEV}(f)|
   &=(\mathrm{Id}\cup
      \mathrm{pre}\cap\widetilde{\mathrm{pre}})^{*}|f|.
\end{aligned}
\]

The second identity grows from `|f|` through states that have at least one
successor in the current approximation and no successor outside it. The
existential `pre` factor prevents a non-`f` sink from being admitted
vacuously.

Image-finiteness is a printed hypothesis of both propositions. It must not be
dropped when these finite-stage union/intersection characterizations are
cited for an arbitrary transition system.

### Proof boundary

Neither proposition is proved or even derived in this chapter. The paragraph
introducing them says that the fixed-point results are “proved in detail in
[Sifakis 79].” The present chapter defines the notation, states Definition 1
and Propositions 1--2, and later demonstrates one calculation. It does not
contain the delegated proofs. Likewise, it calls the transformers monotonic

The related sentence on original p. 345 says that a branching-time logic

not decision-procedure or completeness results proved here.

## Verification procedure

Section 4.2 gives the analyzer's procedure for a program `PROG`, its
translated IPN `N`, and a formula `f` whose propositional variables are
\(F=\{f_1,\ldots,f_n\}\):

1. associate a Boolean variable with every place of `N`;
2. express each `after a` atom in `F` as a predicate on those variables,
   adding places if necessary;
3. express each `enable a` atom in `F` as a predicate on the Boolean control
   variables and program variables;
4. express `Init` from the initial marking and initial program-variable
   values;
5. reduce `N` without transforming places occurring in the predicates
   \(\{|f_1|,\ldots,|f_n|\}\), using rules asserted to preserve the property
   `f`;
6. compute `pre` for the reduced IPN, then evaluate temporal subformulas in
   the order imposed by `f`, simplifying with the sequential-process
   state-graph facts; and
7. if every iteration completes, accept the property exactly when
   \(|f|(q)=tt\) for every state `q`.

The source explicitly says there is “no criterion on the speed of the
convergence” and lets the user impose a maximum number of iterations. If an
iteration produces no result within that maximum, “the analyzer fails to
give an answer.” Thus the described implementation is intentionally
inconclusive under its iteration cap. It does not say that a capped
approximation may be reported as a proof.

The chapter does not supply the IPN-to-`pre` construction as a formula in
marking and guarded-command syntax, the net-reduction rules, proofs that
those rules preserve arbitrary formulas `f`, a convergence test algorithm,
or the representation and simplification algorithms for Boolean predicates.
The outline is therefore sufficient to identify the mathematical method but
not to reproduce the analyzer from this paper alone.

## Worked verification on original pp. 348--349

The only fully worked formula evaluation is

\[
 \mathrm{Init}\Rightarrow
 \mathrm{ALL}\,\mathrm{POT}\,\mathrm{enable}(\mathrm{SENDER}).
\]

With conjunction signs omitted, the initial predicate is

\[
 \mathrm{Init}=s_1m_1a_1r_1\bar Y\bar Z.
\]

The Boolean place variable `s_i`, `m_i`, `a_i`, or `r_i` says that the
like-named Figure 2 place contains a token. The source next gives

\[
 \mathrm{enable}(\mathrm{SENDER})=
 s_1m_1\cup s_2m_1\cup s_2a_2\cup s_3.
\]

It sets \(P_0=\mathrm{enable}(\mathrm{SENDER})\) and computes the `POT`
interpretation with

\[
 P_{k+1}=P_k\cup\mathrm{pre}(P_k).
\]

The translator-generated one-token invariants used in simplification are,
in normalized typography,

\[
\begin{aligned}
s_1\bar s_2\bar s_3\cup
 \bar s_1s_2\bar s_3\cup
 \bar s_1\bar s_2s_3&=T,\\
r_1\bar r_2\bar r_3\cup
 \bar r_1r_2\bar r_3\cup
 \bar r_1\bar r_2r_3&=T,\\
m_1\bar m_2\cup\bar m_1m_2&=T,\\
a_1\bar a_2\cup\bar a_1a_2&=T.
\end{aligned}
\]

The first iteration gives

\[
 \mathrm{pre}(P_0)=s_3\cup r_2\cup r_3\cup a_2\cup m_2,
 \qquad P_1=P_0\cup\mathrm{pre}(P_0)=T.
\]

The paper consequently reports
`POT enable(SENDER) = T`, then
`ALL POT enable(SENDER) = T`, and finally the whole implication as `T`:
“the property is verified.” This is a concrete one-step calculation, not a
general complexity experiment. None of the other invariant, liveness, or
response examples is evaluated in the paper.

## Termination, complexity, and supported state space

No asymptotic running-time or space bound, model-size bound, fixed-point
iteration bound, or analyzer benchmark is stated. There is also no theorem
that the presented implementation terminates on every accepted program. The
explicit operational claim is weaker: the user sets an iteration maximum,
and the analyzer may return no answer.

The conclusion says that fixed-point computation on monotone functions is
the central practical problem. It additionally invokes theoretical
limitations, specifically “non-decidability of the ‘interesting’ system
properties,” but gives no formal decision problem, reduction, or theorem for
that sentence. The practical bottleneck is manipulation, simplification, and
comparison of predicates over many variables.

The then-current CESAR implementation can verify formulas whose variables
are only:

- Boolean;
- enumerated; or
- integer with known bounds.

Enumerated and bounded integer variables are encoded into Booleans,
transparently to the user. This supports a finite Boolean representation in
the stated implementation, but the paper does not derive an explicit
\(2^n\)-style state or iteration bound from it.

The three proposed directions are: approximate fixed points in a lattice,
citing [Cousot 78] and [Clarke 80]; decompose global assertions into local
assertions; and develop a description methodology because proof success
depends strongly on how the description is built.

## Source defects, ambiguities, and non-results

The following are literal source boundaries, not editorial repairs:

1. **Execution sequence:** original p. 344 omits the clauses that the first
   state is the named start and successive states follow `->`; only the
   finite-sink condition is printed.
2. **Boolean semantics:** `false`, disjunction, and implication occur in the
   language vocabulary but receive no separate displayed interpretation
   clauses.
3. **Action identifier:** original p. 347 twice prints `receivack`; the only
   defined program/Figure 2 label is `receiveack`.
4. **Loss spelling:** the code labels are literally `loose` and `looseack`;
   original p. 341 also says the line cannot “loose” all messages and
   acknowledgements.
5. **Unencoded progress assumption:** the prose excludes a permanently cut
   line, but the line programs allow the loss branch forever and the
   semantics supplies no fairness condition.
6. **Citation-key inconsistency:** §2.3.1 prints `[Barlett 69]` once, while the
   introduction and bibliography print `[Bartlett 69]`.
7. **Bibliographic page-range ambiguity:** `[Schwartz 81]` literally prints
   `pp. 46-454`, an implausibly broad range. No correction is asserted here
   because that cited body was not part of this source task.
8. **Reprint metadata:** Springer's and VERIMAG's 2008 HTML title misspells
   `CONCURRENT` as `CONURRENT`; both the 1982 body and inspected reprint PDF
   page spell it correctly.
9. **Nonstandard iteration glyph:** the source's superscript `x` for
    intersection of all finite iterates is explicitly defined; it must not be
    silently read as a multiplication or an unexplained fixed-point symbol.
10. **No general proof in body:** Proposition 1 and Proposition 2 are cited
    results whose proofs are outside this chapter. The translation-safety and
    reduction-preservation claims are also asserted without proof here.
11. **No full decision/complexity result:** the paper gives neither a
    satisfiability decision procedure for `L` nor a model-checking complexity
    theorem. It explicitly permits analyzer failure at a user-set iteration
    cap.
